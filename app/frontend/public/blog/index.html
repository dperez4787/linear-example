Case study · Agentic software delivery

An agentic SDLC, end to end: local planning, remote execution

A production CRUD service — authenticated, deployed, and maintained by a team of Claude Code agents driven from Linear tickets. The final feature was specified locally and implemented, tested, and shipped entirely by remote agents. Every claim links to a commit, pull request, or workflow run in the public repository.

Daniel Perez · July 2026 · 13 min read · github.com/dperez4787/linear-example

Initial goals

  1. Build a complete product, not a demo: a CRUD service with a web UI, backed by a managed database, fully authenticated with Google sign-in, and deployed to production on managed infrastructure.
  2. Run the entire SDLC through agents with defined roles — product owner, architect, developer, tester — coordinated through a real ticketing system, with every quality gate enforced structurally rather than by convention.
  3. Make the system maintainable by remote agents: after the initial build, a feature should ship by moving a ticket on the board — implementation and verification running in the cloud on metered API credits, with no development machine involved.
  4. Hold everything to production engineering standards: infrastructure as code, no long-lived credentials, secrets in managed stores, and quality gates enforced by the platform — the practices a team would defend in an enterprise review, not demo shortcuts.

All four were met. The final validation was a non-trivial feature — converting the service's REST API to GraphQL — that went from ticket to production with the only human actions being two status changes and a merge click.

Architecture

Phase I

Bootstrapping: the team is version-controlled

The first commits contain no application code. They establish a team of four agents — checked into the repository as role definitions — and a project handbook (CLAUDE.md) covering stack decisions, code conventions, and the git workflow every agent must follow: c82385b establishes the baseline, 641a676 pins the toolchain contract, 3ac2573 defines the branch-and-PR workflow. Notably, 39b7451 records the remote-execution decision — GitHub Actions over hosted schedulers — before a single endpoint existed.

Two rules from this phase carried the entire experiment:

  • Acceptance criteria on the ticket are the specification. The tester verifies against what the Linear issue states, never against what the developer reports having built. This made the ticket the interface between roles — which is precisely what later allowed a role to move to a machine I don't own.
  • Agents never merge. Every ticket PR opens as a draft; only the tester may lift the draft, and only after every criterion passes. GitHub refuses to merge a draft, so the review order is enforced by the platform rather than by memory. Commit cbe8242 — “Make the tester, not memory, gate the merge” — records the moment that principle was made structural.

Phase II

The local agentic SDLC

The application was built ticket by ticket, each flowing through the same loop: the product owner writes the ticket, the architect records design decisions in docs/architecture.md, the developer implements on the ticket's branch and opens a draft PR, and the tester checks out that branch, adds tests as its own commit, and posts a pass/fail verdict on both the issue and the PR before lifting the draft. Each Linear ticket maps directly to its commits on main:

The commit history shows the process doing real work. On DAN-8, the tester found that React StrictMode double-fired the initial fetch and committed a failing acceptance test (d02593f, “currently red”) before the developer's fix landed (6a26256) — test-first pressure applied by one agent to another, because the handbook assigned them adversarial roles.

Failures from this phase became conventions the same day. A documentation PR with a ticket ID in its title caused Linear to silently auto-close a still-open ticket on merge; ticket IDs now appear in commit subjects and PR bodies only. Agents execute in non-interactive shells that skip normal profile loading; the resulting “missing Node” failures produced the handbook's environment contract. The handbook functions as institutional memory — every agent session, local or remote, starts by reading it.

Phase III

Deployment and validation

Fourteen tickets took the application to production: a container image, Terraform for the deploy identity (Workload Identity Federation — no service-account keys exist anywhere in the system), Cloud Run and Firebase Hosting deploy workflows, and Google sign-in with ID-token verification gating the API.

This phase surfaced the most important design boundary in the project: some work must not be done by an agent. Enabling billing, pasting a database credential into a secret store, authorizing OAuth — the product owner labels these tickets [USER-EXECUTED]; the agent writes the runbook and a human executes it. The seam is explicit in the ticket record below.

Infrastructure as code, treated as a commitment

The environment is not clicked together. What began as a manual runbook was explicitly replaced by Terraform (48732b8, “Replace the manual DAN-11 runbook with Infrastructure as Code”), with remote state in a GCS backend. The commitment shows most clearly in the adoption tickets: when an API had to be hand-enabled in the console to unblock work, a ticket (DAN-20, DAN-24) was filed to bring that resource under Terraform — drift is reconciled into code, not tolerated. The same posture runs through the rest of the system: deploys authenticate through Workload Identity Federation so no service-account key exists to leak; the database credential lives in Secret Manager and a gitignored local file, never in the repository; and application conventions — a single error middleware, a pooled Mongo client, tests colocated with what they test, no data-layer calls in route handlers — are written in the handbook and enforced by the tester on every ticket. Maintainability was designed as a property of the system, not a hope about future diligence.

Validation stayed concrete throughout. DAN-17 and DAN-18 are bug tickets filed by agents running the deployed system — the second documenting that Cloud Run intercepts /healthz before it reaches the container, a finding no unit test produces. The tester's refusal to mark criteria passed without observed behavior is what surfaced both.

Phase IV

Remote execution: the board becomes the trigger

Through Phase III, agents still ran in sessions on my machine. The final goal was precise: planning stays local, but once a ticket reaches a designated status, implementation and verification should run remotely — on my API credits, on infrastructure I don't have to keep awake.

Selecting the mechanism

I evaluated hosted sandboxes (no external event triggers), scheduled cloud agents (cron-based, and unaware of in-repo agent definitions), Linear's native agent delegation (manual assignment per issue), and a self-hosted Agent SDK service (workable, but requires operating a server). The selected design is deliberately minimal: a GitHub Actions workflow that polls Linear every five minutes — one GraphQL request per poll. The deciding factors:

  • The agents were already in the repository. Claude Code on a CI runner reads .claude/agents/ and CLAUDE.md from checkout exactly as a local session does. The remote developer is the same developer, byte for byte.
  • Push delivery costs more than it returns. Linear webhooks cannot attach the authentication header GitHub's dispatch API requires, so webhooks mean operating a relay service plus an access token. Polling requires neither, spends no model tokens when the board is quiet, and a five-minute pickup latency is immaterial for ticket work.

The setup is fully public: the workflow definition (commit 3d69080) and every agent invocation, with logs, can be inspected directly.

Concurrency: the status change is the claim

When the poller finds a ticket in Ready for Dev, the job's first action — before any model call — is moving the ticket to In Progress. The board column functions as the mutex: a second scan cannot claim what has left the trigger column, a per-ticket concurrency group covers the race between adjacent polls, and the claim is visible to humans for free, because the claim signal and the board are the same artifact. The tester leg reuses the team's existing In Review status and stamps completed runs with an agent-tested label so no ticket is verified twice. A failed criterion moves the ticket back to In Progress; the draft is never lifted; agents still never merge.

One setup mistake is worth recording because of what it generalizes to: I armed the pipeline (merged the workflow) while the feature ticket sat in the trigger column and its architecture document was still an open PR. The remote developer would have begun implementing against a design not yet on main. The recovery was one status drag, but the lesson stands — once a board column can initiate spend, merge order is production configuration.

The validation run

The pipeline's first feature was deliberately substantial: DAN-25, converting the entire REST API to GraphQL. The product owner drafted the ticket with mechanically checkable criteria; the architect recorded the design (library selection, schema, error mapping — including catching that one REST route had never actually been implemented) in 4d1e4fb; I merged the design and moved the ticket to Ready for Dev.

The result is pull request #26 — authored by github-actions[bot], implementing commit 021bc2f and tester commit 34ab0f7. The tester's verdict comment on the PR enumerates every acceptance criterion with the command-level evidence: full CRUD via GraphQL, field-scoped validation errors, the authentication gate intact, all five removed REST routes returning 404, and the frontend diff confined to the API layer — verified by inspecting the diff, not by trusting the developer's report. On merge, the existing deploy workflows shipped the feature to Cloud Run and Firebase Hosting, and Linear closed the ticket.

Closing

What actually transferred

The remote capability was never the workflow file. It was that the preceding phases had moved every interface out of my head and into artifacts a runner can read:

  • The specification lives on the ticket — acceptance criteria an adversarial tester enforces.
  • The design lives in the repository — docs/architecture.md, written before implementation.
  • The conventions live in the handbook — CLAUDE.md, read at the start of every session.
  • The team lives in version control — .claude/agents/, identical locally and remotely.
  • The safety lives in the platform — draft PRs, status-as-claim, and a merge button only a human can press.

By the final phase, my machine contributed nothing but review judgment at three checkpoints. The remote setup added no new capability — it removed the last dependency. If an agentic process still requires its operator present to function, the missing piece is usually not a cloud feature; it is an interface still living in someone's head.

All evidence is public: the repository, the remote agent invocations, and the bot-authored pull request. The Linear workspace is private; each ticket referenced here is traceable through its linked commits and the tester verdicts on the pull requests.
