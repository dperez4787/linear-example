### Acceptance criteria

* `GET /api/records` returns `200` with body `{records: [...]}` (an object, never a bare array); an empty collection returns `{records: []}`.

* `POST` with `notes` longer than 1000 chars returns `400` with `{error:{message, field:"notes"}}`.
* A client-supplied `id`/`_id` in the POST body is ignored, not persisted.
* Errors are produced by throwing in the schema/data layer and mapped by one Express error middleware — no inline `res.status(500)`, and no Mongo driver calls inside route handlers.

The middleware calls `verifyToken(token)` and gates on whether it resolves. Tests inject a stub that resolves for a known fake token and rejects otherwise — no emulator, no network, no extra process.

**What this design does not prove, stated plainly:** the stub is not `firebase-admin`, so the suite never exercises real signature verification, token expiry, or the `aud`/`iss` checks. The production `verifyIdToken` path is exercised **only live**. "A real Google-issued token is accepted by the deployed service" therefore stays a user-attested criterion — it is not a gap the tester can close, and a green suite must not be read as proving the verifier works. The emulator would close it, at the price of a mandatory running process on every `npm test` and CI run, including the majority of tests that touch neither Mongo nor auth.

### Config surface: no new env var

The project ID (`project-d60a83c1-2c60-4d51-ad0`) is a **constant in the backend**, not an env var — it is a public, stable identifier already hardcoded across `firebase.json`, `CLAUDE.md`, and the image path. **No new row in the Environment table.** No key, no Secret Manager secret, no GitHub Secret: `firebase-admin` picks up ADC from the runtime SA on Cloud Run, and the public keys it verifies signatures against come from an unauthenticated Google endpoint.

`firebase-admin` initializes **lazily** — on first verification, never at process start — so the server still boots and `/health` still returns `200` with no `.env`, no ADC, and no network. That is what keeps DAN-17's no-`.env` path and DAN-5's boot-before-connect behavior intact. **Boot must not import-and-initialize in a way that reaches the network.**

* **Inject the verifier through `createApp`.** No module global, no monkey-patching `firebase-admin`. The seam is a design boundary; reach for a global and it is lost.
* **Mount the gate on `/api/records`, after `/health`, before the router.** `/health` stays unauthenticated and Mongo-free — it was renamed from `/healthz` in DAN-18 precisely because the platform swallows that exact path, and it must keep returning `200` while Mongo is down.
