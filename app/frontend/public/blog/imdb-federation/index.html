Federating IMDb: an agentic build at three speeds

Goals

Functional

  1. An extremely snappy, rich IMDb data experience — every public IMDb dataset available through one UI: titles, people, ratings, episodes, crews, regional titles, and the 100-million-row principals collection.
  2. Sort by popularity, everywhere — titles rank by vote counts for free; people needed a materialized popularity score computed from the work they're known for.
  3. Search facets — vocabulary dropdowns (every genre, every credit category) and live counts that narrow with the filter: “Drama (1,204)”.
  4. Images for titles — poster art in the browsing experience, not just rows of text.
  5. Enterprise-grade, field-level governance and security — individual fields like Rating.numVotes or Name.birthYear grantable per role, administered from a control-plane UI, enforced live with no redeploys.

Technical

  1. Use AI to build the application — at varying degrees of formality. One system, three delivery styles: full ticket-driven rigor, lightweight file-based tickets, and pure vibe coding. Measure what each buys.
  2. A proof-of-concept of open-source GraphQL federation — WunderGraph Cosmo composing eight Netflix DGS subgraphs, with custom Go router modules instead of a commercial control plane.

Architecture: six repositories, one system

Every artifact below is a repository on my GitHub profile. The centerpiece is imdb-federation — a single Maven mono-repo holding all eight Java subgraphs as modules. One shared Dockerfile parameterized by module, one paths-filter matrix that builds only what changed, one common/ library — eight Cloud Run services out the other end. The mono-repo is what made “stamp out seven more subgraphs from the proven pattern” a one-day exercise instead of seven repo setups.

The build

Two entities, eight owners of the truth

The federation design fell out of the data. Two things in this world have identity — a title (tconst) and a person (nconst) — so the graph has exactly two entities. Each MongoDB collection became a subgraph that either owns an entity (titles, names) or contributes fields to it (ratings, episodes, crew, akas, principals), and the eighth — the orchestrator — owns search. The load-bearing trick is the key stub: when the crew subgraph says “directed by nm0005690,” it returns a Name stub marked resolvable: false, and the router hydrates the person from the names subgraph in a parallel _entities hop. No subgraph ever reads another subgraph's collection.

The riskiest assumption was proven first: that a DGS entity fetcher could batch through a DataLoader so N representations collapse into one indexed $in query rather than N+1 lookups against a 100M-row collection. The keystone subgraph shipped with a Mongo CommandListener that counts every command the driver sends — assertThat(counter.count("find")).isEqualTo(1) — and that batching-proof assertion became house style across all 114 tests. With the keystone green, the remaining subgraphs were stamped from the same pattern and went green on the first full run.

Search earns its own collections

“Top-rated Sci-Fi from the 70s and 80s” is not a query the source collections can answer: genres are comma-joined strings, ratings live apart from years, and the import pipeline atomically replaces any collection you dare to index. So the orchestrator subgraph owns two derived collections it rebuilds on demand — genres split into real arrays, ratings merged in, and a materialized popularity for people (explode 45M known-for credits, join 1.7M rated titles, sum the vote counts — Bryan Cranston outranks a prolific-but-obscure character actor, exactly as a search box should behave). Facets come in two typed flavors — materialized vocabularies and contextual $facet counts capped at the same 10k budget as totals — because the tempting alternative, a GraphQL field that accepts a raw aggregation pipeline, is an injection surface, an unbounded-cost surface, and a schema-contract vacuum. The API reports what it approximated (titleCandidatesCapped) instead of pretending exactness over 12.6M rows.

The router is the only door

Auth splits into two boundaries with two token types, and the subgraphs needed zero auth code for either. Client → router: stock Cosmo JWT verification against Google's JWKS — anonymous requests die with 401 before any GraphQL work. Router → subgraphs: Cloud Run IAM. The subgraphs deploy with --no-allow-unauthenticated, and the router's subgraphtoken module mints a Google-signed ID token per subgraph audience; a direct call to any subgraph gets 403 from Google's front end before Spring Boot ever sees it. That perimeter is what makes single-point field enforcement honest.

Field-level governance: declare at the edge, decide at the center, enforce at the gate

The governance plane follows one rule — each layer does exactly one job, and no job is done twice:

  • Subgraphs declare. A custom DGS directive marks sensitive fields in the schema, next to the code that owns the data: numVotes: Int! @governed(reason: "vote counts are analyst-only"). At startup each subgraph registers its declarations with the policy service. It never evaluates authorization at runtime.
  • The policy service decides. imdb-policy-service is the system of record: governed fields, role policies, personas, and an append-only audit log in MongoDB. It publishes a versioned policy bundle and mints demo persona JWTs — identity and policy in one coherent system.
  • The router enforces. The fieldauth Go module polls the bundle (ETag, ~15s, fail-static on outage), resolves every selected field of an operation to a schema coordinate — aliases, fragments, union spreads included — and rejects violations with a PERMISSION_DENIED error naming the exact coordinates.
  • The control-plane UI administers it. The admin UI is where governance becomes visible: a graph view of every governed field and its live policy, a per-subgraph view of @governed declarations exactly as registered, a playground that mints a persona token and replays a real query, and the audit trail — who changed what, when.
Verified live

Against production: an analyst reads Rating.numVotes (2.6M votes for Game of Thrones); public gets PERMISSION_DENIED naming the coordinate; an admin grant flipped the outcome live within one 15-second poll — bundle revision 2 → 3, no deploy — and the revert re-denied. The audit trail records every step.

The experiment

Three speeds of formality

The technical goal worth the most was not the federation — it was watching the same developer-agent capability deliver under three different process regimes, and seeing what each one costs and buys.

Speed 1 · Vibe codingimdb-federation & the routerfastest

The federation itself — eight subgraphs, the custom router, two auth boundaries, the whole 211M-document graph — was built by vibe coding: conversational sessions with Claude Code, no tickets, no formal acceptance criteria. It was by far the fastest mode; a keystone-first strategy and a house rule that every subgraph proves its batching arithmetic in a test supplied the rigor the process didn't.

Speed 2 · File-based ticketsimdb-browserthe optimization

The browsing UI ran one notch more formal: its implementation was driven by tickets maintained as files in the imdb-data-pipeline repository — not in Linear. An optimization: the structure of scoped work items and acceptance criteria, without the ceremony of a ticketing system, a board, or a polling pipeline. Tickets keep an agent honest even when they're just markdown in a sibling repo.

Speed 3 · The full agentic SDLClinear-examplethe rigor

At the formal end sits the first post in this series: a product owner, architect, developer, and tester coordinating through Linear, remote agents claiming tickets from a board, draft-PR gates the platform enforces, and a human whose only actions are two status changes and a merge click.

The point of the spectrum is that formality scales to the stakes — and to the author. Vibe coding was the right speed for an expert-steered infrastructure build where the operator could supply judgment interactively. File tickets were right for a UI with clear scope and a fast feedback loop. And the fully formal end is not bureaucracy for its own sake: when acceptance criteria on a ticket are the specification, and implementation and verification run remotely against that specification, the person driving delivery no longer has to be an engineer. That is the trajectory the first post now states explicitly: dial the formality up and the same pipeline lets product owners and designers drive their own application development — engineering rigor supplied by the process, not gated on engineering availability.

Where it stands

Live, governed, and one endpoint wide

Eight subgraphs, the router, and the policy service are live on Cloud Run behind two auth boundaries. The full dataset is imported weekly, searchable, faceted, and governed at the field level from a control-plane UI. The browsing experience consumes one endpoint and one contract: entity queries, filtered searches with live facet counts, a unified search box, and popularity-ranked everything.
